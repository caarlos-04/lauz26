## 1. What we are building

A **"design your own life"** game in which the user watches **their digital twin** live ten years:
every decision changes their life and their money, and at the end they understand **which changes led to their final state**.

Feedback from the organisers that drives the design:
- **The story is what matters**: the person's digital twin and the **narrative of the changes** that lead to the final state.
- **Monte Carlo is too simple**: we have to go further. We replace it with an exactly solved decision tree, parallel lives and sensitivity analysis (section 9).

It covers two challenges at once:
- **AI Financial Twin** (main challenge, concept by Stefania Stan). Principle: *"Don't predict the future. Make it explorable."*
  The (draft) rubric weighs: financial modelling and correctness 25, scenarios and counterfactuals 20, execution and validation 15,
  user experience 15, innovation 15, transparency 10. Judges' questions: *which assumptions matter most?,
  how does a decision change the state?, how did you validate it?, what happens if a constraint is violated?*
- **JetBrains Kotlin Multiplatform**. The app must run on **at least 2 platforms**; scoring rewards how much logic
  lives in `commonMain`, plus dark/light mode, localisation, Compose Multiplatform, a Kotlin backend and shared AI logic (Koog).
  Extra points for *Agentic Development* with JetBrains Air (document what each agent did and what we corrected).

## 2. Decisions taken

| Topic | Decision |
|---|---|
| Stack | Kotlin Multiplatform + Compose Multiplatform |
| Platforms | Android + Desktop (JVM) |
| Languages | ES / EN |
| Time | Less than 24 h → very trimmed MVP |
| Profile | The user enters their own through a multiple-choice interview. **Alexia** (20, student, Lausanne, CHF 8,000) is preloaded as a demo profile in case it fails |
| Digital twin | One **`FinancialStatement`** per step with all the information about the person (see `docs/financial-statement.md`): money (computed by the engine) + life: facts (education, occupation, city, housing, family) and milestones (`flags`), which only events change, explicitly |
| Measured non-financial dimensions | **No** (no wellbeing, stress, etc.: there is no data) |
| Game | ~5 turns of 24 months (10 years, 120 months) |
| Uncertainty | Each uncertain number of a decision (salary, tuition, pay rise, rate, months...) is a distribution like a normal fitted to the data; the **luck** of the decision is the percentile drawn (no pessimistic / neutral / optimistic cases) |
| Story | Short text each turn (the outcome sentence with the drawn numbers) + a **full chronicle** generated by the LLM at the end, from computed facts |
| Uncertainty and analysis | **No Monte Carlo.** Exact decision tree (optimal strategy and parallel lives), sensitivity and break-even point |
| Constraints | User's minimum liquidity; negative cash is financed with interest |
| Money | `Double` in CHF (consistency tests with tolerance). No taxes (documented limitation) |
| LLM | **Not decided yet**, but **free** (section 10). Hidden behind the `FutureSelfChat` interface |
| Persistence | Game kept in memory during the demo (whether to save it to disk is still open) |

Terminology: **luck** (the percentile of a decision's uncertain numbers), **fact**, **milestone** (`flag`), **moment** (`StoryBeat`), **parallel life**.

## 3. Experience and game loop

> Since the action-pool redesign the game is a **tree of decisions**: full description in
> [`decision-tree.md`](decision-tree.md).

```
Interview ─► Initial twin (money + life)        Luck mode chosen at the start (same at the same age / own per decision)
                 │
   ┌─────────────▼─────────────────────────────────────────────────┐
   │ Decision N: every action the person can take now (the pool)   │
   │   "Carry on as you are" · "Do a master's" · "Share a flat" ... │
   │   no balances shown before deciding                            │
   │ The user picks one → the luck of the moment (a percentile)     │
   │ draws its uncertain numbers (salary, tuition, rent...)         │
   │ → maybe a shock nobody chose (job loss) → 24 months pass       │
   └─────────────┬─────────────────────────────────────────────────┘
                 │ (5 decisions; go back to any moment and decide something else: a new branch)
                 ▼
 End: life line · waterfall "where your net worth comes from" · map of the lives you decided
      · chronicle · chat with your self of any moment
```

- **The player drives the life**: at each node the pool shows the actions whose `requires` match the statement. What
  you did changes what you can do next (after a master's you can work; with negative cash you can take a loan).
- **Before choosing**, each action shows what it is and which numbers depend on luck (their usual range), not balances.
- **When choosing**, the luck of the new node (from the seed and the luck mode) is the percentile every uncertain number
  of the action is drawn at. The balances are shown only after deciding.
- **Nothing advances on its own**: a branch exists only if the user decided it. Going back to a moment and deciding
  something else opens a new branch; nothing already lived is lost.
- **At the end** (all computed by the engine; the LLM only tells it):
  1. **Life line** with age, decisions, shocks and key moments (lowest cash, goals, life changes).
  2. **Waterfall** of net worth: where every franc comes from and goes to.
  3. **Map of lives**: every branch the user explored, to compare them and to go back.
  4. **Chronicle** of your life and **chat** with your self of any moment.

## 4. Architecture

Almost everything in `commonMain`:

```
commonMain
├─ model/     data classes (section 5)                      [shared contract]
├─ engine/    TwinEngine (docs/simulator.md section 6) behind the UI's GameEngine interface: monthly step, effects, luck, financing, life changes,
│             moments (StoryBeat), attribution, tree of decisions (actions, luck modes, shocks), sensitivity
├─ events/    event catalogue and selection based on the current life
├─ data/      JSON loading (flow model, macro trends, events, facts, assumptions, interview)
├─ ai/        FutureSelfChat interface and chronicle (swappable LLM implementation)
└─ ui/        Compose screens: interview, dilemma, resolution, life line, results, chat
androidMain / desktopMain  → only start-up, files and API key
tools/        offline Python scripts (flow model, macro trends, reference simulator and game, event validation)
content/      game content in JSON (events, facts, assumptions), written by Dev C
```

Kotlin data classes: `composeApp/src/commonMain/kotlin/com/lauzhack/twin/model/` (not compiled yet; see issue #5).

Principles:
- The engine is a **pure, immutable function**: `apply(statement, action, luck) → newStatement`. Easy to test and reproduce.
- **The engine computes the money; events change the life.** Nothing is made up along the way.
- Events are **JSON data**, not code. The app only reads JSON (the CSVs are processed offline in `tools/`).
- **Nobody changes `model/` without telling the others**: it is the contract.

## 5. Data model (data classes)

Conventions:
- All `@Serializable` (kotlinx.serialization). All **immutable** (`val`, `copy()` to change).
- Money: `Double` in **CHF**. Interest/return rates: **annual fraction** (0.05 = 5 %).
- Time: `month` = month index since the start of the game (**0..120**). `startMonth` as text `"2025-01"`.
- Probabilities: `0.0..1.0`. Ids are stable `String`s.
- **Content** texts (events, facts, milestones) are inline: `LocalizedText = Map<Lang, String>`.
  Fixed **UI** texts use i18n keys.

### 5.2 Profile and twin state: `FinancialStatement`

The twin's state at each step is a **`FinancialStatement`**: the person at one point in time, with only what the
datasets have and what the simulator needs to produce the next statement (one cash balance, one investment portfolio,
at most one loan, one income, one rent, as in the data). Net worth, goal progress and ratios are computed, not stored.
**Full schema, origin of each field and decisions: [`docs/financial-statement.md`](financial-statement.md).**

```kotlin
data class FinancialStatement(
    val profileId: String, val month: Int, val period: String,     // month 0 = opening, "2025-01-01"
    val person: Person,                         // displayName, age, employment, household, facts, flags
    val cashChf: Double, val investmentsChf: Double, val loan: Loan?,
    val monthlyIncomeChf: Double, val monthlyRentChf: Double,
    val eventExpensesChf: Map<ExpenseCategory, Double>,           // recurring expenses added by events
    val cashFlow: CashFlow?,                    // the month's flows by category; null at month 0
    val goals: List<Goal>,                      // name, targetChf, targetDate, priority
    val pendingChanges: List<PendingChange>     // decided by events, applied when their month arrives
)
```

**Studying and working are independent.** The dataset's `employment_status` mixes both in one value (`student`,
`employed`...). In the statement they are separated:
- **Studies** → `person.facts.EDUCATION` (studying ⇔ the value ends in `_IN_PROGRESS`).
- **Work** → `person.employment`. A student without a job is `NOT_WORKING`; a working student is `PART_TIME` (or `EMPLOYED`)
  **and** still has `EDUCATION: MASTER_IN_PROGRESS`. Nobody "stops being a student" when they start working.
- When loading the dataset: `student` → `NOT_WORKING` + `EDUCATION: BACHELOR_IN_PROGRESS`; every other value stays as is
  with `EDUCATION: UNKNOWN`.
- **Simulator feature** `studying` = `EDUCATION` ends in `_IN_PROGRESS`; work comes from `employment`. The flow model
  learns their effects separately (e.g. studying −20 % on living costs, December bonus only when employed).
- Events: `requires.employment` filters on **work**, `requires.facts.EDUCATION` on **studies**.

### 5.3 Events (game content, in JSON)

Contract defined by Dev C. Content lives in `content/events.json`, validated with `tools/validate_events.py`
(writing guide in `content/README.md`). Which catalogue scenarios became events, and why the rest were dropped:
[`docs/events-mapping.md`](events-mapping.md).

```kotlin
typealias LocalizedText = Map<Lang, String>   // {"ES": "...", "EN": "..."}

data class ActionCatalog(val version: Int, val actions: List<Action>, val shocks: List<Shock>)   // content/events.json v4

data class Action(                  // something the player can decide (docs/decision-tree.md)
    val id: String,                 // "A-master" (unique); "NOTHING" = carry on as you are (always available)
    val category: String,           // category from scenario-catalog.csv, e.g. "Education & skills"
    val title: LocalizedText,
    val description: LocalizedText,
    val requires: Requirements? = null,   // null = available to everyone
    val repeatable: Boolean = false,      // false = at most once per life (path of the tree)
    val earliestTurn: Int = 0,
    val sources: List<String>,      // where each number comes from (shown in the UI)
    val effects: List<Effect>,      // with the median of every uncertain number
    val uncertain: List<Uncertain>, // the numbers that depend on luck, drawn at the decision's percentile
    val outcome: LocalizedText      // the story of the outcome: {name} = an uncertain number as drawn
)

data class Shock(                   // something nobody chooses (job loss), drawn once per turn
    val id: String, val category: String, val title: LocalizedText, val description: LocalizedText,
    val requires: Requirements? = null,   // checked after the action's immediate changes
    val probability: Double,        // chance per turn of 24 months
    val sources: List<String>, val effects: List<Effect>, val uncertain: List<Uncertain>, val outcome: LocalizedText
)

// A two-piece normal through three values of the data, on the value (NORMAL) or its logarithm (LOGNORMAL); QUANTILE =
// the luck itself (the quantile of a new rent). better = the side good luck gets.
data class Uncertain(val name: String, val law: Law, val median: Double, val low: Quantile, val high: Quantile,
                     val better: Better, val step: Double, val format: String, val targets: List<Target>,
                     val min: Double? = null, val max: Double? = null)

// All present fields must match. Evaluated at the start of the turn.
data class Requirements(
    val employment: List<Employment>? = null,
    val household: List<Household>? = null,
    val minAge: Int? = null,        // person.age
    val maxAge: Int? = null,
    val facts: Map<FactKey, List<String>>? = null,   // fact value must be one of these
    val flagsAll: List<String>? = null,     // must have all these milestones
    val flagsNone: List<String>? = null,    // must have none of these
    val minCashChf: Double? = null,
    val maxCashChf: Double? = null          // e.g. 0 -> only when cash is negative
)

// JSON discriminator: "type" (use @SerialName). Offsets are months relative to the start of the turn (s).
sealed interface Effect {
    // Money
    @SerialName("set_income")          // the income becomes monthlyChf from s+offset on. Permanent.
    data class SetIncome(val monthlyChf: Double, val startOffsetMonths: Int = 0) : Effect
    @SerialName("income_factor")       // the income is multiplied by factor (data ratio) for `months` (null = permanent)
    data class IncomeFactor(val factor: Double, val startOffsetMonths: Int = 0, val months: Int? = null) : Effect
    @SerialName("set_household")       // new household; must come with the HOUSING / FAMILY facts it implies
    data class SetHousehold(val household: Household, val startOffsetMonths: Int = 0) : Effect
    @SerialName("market_rent")         // a new home: market rent for the city and household (rent model), at a quantile
    data class MarketRent(val quantile: Double = 0.5, val startOffsetMonths: Int = 0) : Effect
    @SerialName("income_delta")        // the income changes by deltaChf (negative = cut) for `months` (null = permanent)
    data class IncomeDelta(val deltaChf: Double, val startOffsetMonths: Int = 0, val months: Int? = null) : Effect
    @SerialName("expense_delta")       // extra monthly expense (negative = saving) for `months` (null = permanent)
    data class ExpenseDelta(val category: ExpenseCategory, val deltaChf: Double,
                            val startOffsetMonths: Int = 0, val months: Int? = null) : Effect
    @SerialName("one_off")             // one-time cost at s+offset (negative = one-time gain)
    data class OneOff(val chf: Double, val startOffsetMonths: Int = 0) : Effect
    @SerialName("add_liability")       // a personal loan paid out to cash at s; annuity over termMonths
    data class AddLiability(val principalChf: Double, val annualRate: Double, val termMonths: Int) : Effect
    // Life
    @SerialName("set_employment")
    data class SetEmployment(val employment: Employment, val startOffsetMonths: Int = 0) : Effect
    @SerialName("set_fact")            // value must exist in content/facts.json for that key
    data class SetFact(val key: FactKey, val value: String, val startOffsetMonths: Int = 0) : Effect
    @SerialName("add_flag")            // flag must be declared in content/facts.json
    data class AddFlag(val flag: String, val startOffsetMonths: Int = 0) : Effect
}
```

How the engine translates them (no hidden state): every effect becomes one or more `PendingChange`s of the statement,
applied by the simulator at the start of their month (`month = s + offset`):
- `set_income` → `monthlyIncomeChf`; `income_delta` → `incomeDeltaChf`; `income_factor` → `incomeFactor` (both undone
  after `months`).
- `set_household` → `household`; `market_rent` → `marketRentQuantile` (the rent is computed once the month's city and
  household changes are applied).
- `expense_delta` → `expenseCategory` + `expenseDeltaChf` (and its reversal); `one_off` → the same for one month.
- `add_liability` → `loan` (paid out to cash, merged with an existing loan: the data have at most one per person).
- `set_employment` / `set_fact` / `add_flag` → the life change; it emits a `LIFE_CHANGE` `StoryBeat`.
- `tools/game.py` implements these rules in Python as a **reference** for the engine tests.

### 5.5 Game

The tree of decisions and its rules: [`decision-tree.md`](decision-tree.md).

```kotlin
data class DecisionTree(            // what is kept: one snapshot per decision taken
    val seed: Long, val luckMode: LuckMode, val preferences: Preferences, val config: GameConfig,
    val nodes: Map<String, DecisionNode>          // id = path of action ids, "" = start
)
data class DecisionNode(val id: String, val parentId: String?, val depth: Int, val actionId: String?,
                        val luck: Double?, val shockId: String?, val state: FinancialStatement)
enum class LuckMode { SAME_LEVEL, FULL_RANDOM }

// One life, from the start to a node: the view the screens, the chat and the analysis read (derived, not stored).
data class GameSession(
    val initial: FinancialStatement,     // month 0
    val seed: Long,                 // same seed + same decisions => same life
    val preferences: Preferences,
    val turns: List<Turn>,          // the decisions on the way to the node, in order
    val config: GameConfig,
    val luckMode: LuckMode
)

data class GameConfig(val horizonMonths: Int = 120, val monthsPerTurn: Int = 24, val maxTurns: Int = 5)

data class Preferences(             // from the interview; shown to the user (weights are value judgements)
    val objective: Objective,       // GROWTH, BALANCED, SAFE
    val minCashChf: Double,         // personal liquidity floor
    val penaltyChfPerMonthBelowMin: Double  // GROWTH 0, BALANCED 500, SAFE 3000 (Assumptions defaults)
)

data class Turn(
    val index: Int,
    val actionId: String,           // NOTHING = carried on as before
    val luck: Double,               // 0..1: the percentile of the uncertain numbers (seed + luck mode)
    val values: Map<String, Double>,     // the uncertain numbers as drawn (salary, tuition...)
    val shockId: String?, val shockLuck: Double?, val shockValues: Map<String, Double>, val shockMonth: Int?,
    val stateAfter: FinancialStatement,  // end of the turn; state before = previous turn's stateAfter (or initial)
    val beats: List<StoryBeat>      // story moments produced during this turn
)

// No preview of balances before choosing: the outcome is seen after the decision.
```

### 5.6 Story, analysis and results

```kotlin
// A story moment. Structured data only: the UI renders it with templates and the LLM narrates it. No prose here.
data class StoryBeat(
    val month: Int,
    val age: Int,
    val kind: BeatKind,
    val eventId: String? = null,
    val data: Map<String, String> = emptyMap()  // e.g. "cash" -> "-39573", "fact" -> "EDUCATION", "value" -> "MASTER"
)

// Where the net worth comes from. Invariant: start + sum(items) == end (tested).
data class Attribution(
    val startNetWorth: Double,
    val items: List<AttributionItem>,
    val endNetWorth: Double
)
data class AttributionItem(
    val key: String,                // "income:salary", "expense:rent", "expense:groceries", "loan_interest",
    val chf: Double                 // "financing_cost", "investment_growth": signed contribution over the whole game
)
// What each decision contributes comes from comparing branches of the tree (same luck in SAME_LEVEL).

data class Stats(
    val finalNetWorth: Double,
    val minCash: Double,
    val monthOfMinCash: Int,
    val monthsNegativeCash: Int,
    val monthsBelowMinCash: Int,    // vs Preferences.minCashChf
    val financingCostChf: Double,
    val goalsReached: List<String>,
    val goalsMissed: List<String>
)

// "Your story would change if..." (section 9).
data class SensitivityItem(
    val parameter: String,          // id from Assumptions.sensitivity
    val lowValue: Double, val highValue: Double,
    val utilityGapAtLow: Double,    // utility(A) - utility(B) for the analysed decision
    val utilityGapAtHigh: Double,
    val breakEven: Double?          // parameter value where the better option flips; null if it never flips in range
)

data class GameResult(
    val session: GameSession,
    val stats: Stats,
    val attribution: Attribution,
    val beats: List<StoryBeat>,     // whole life line
    val sensitivity: List<SensitivityItem>      // for the first decision
)
```

| **P12 Chat** | C | `ChatContext`, `Persona`, history, question | Prompt with the whole context; the LLM only explains | `ChatMessage` |

### Flow rules
- **Single source of truth**: the tree of decisions (`DecisionTree`, one snapshot per decision); `GameSession` is the view of one life and `GameResult` its analysis. The UI and the LLM read from there.
- **The LLM never computes**: it receives `ChatContext` and writes. If a number is missing, it says it does not know.
- **Reproducibility**: same seed + luck mode + decisions ⇒ same life. The luck of a node depends only on the seed, its depth and (FULL_RANDOM) its path.
- **Preview ≠ resolution**: the preview is deterministic; the resolution uses the luck.
- **C produces the content JSON** and A and B consume it; the format is the one in section 5.

## 7. Engine calculation rules

**Start of the turn (month `s`):** first the pending life changes with `month <= s` are applied (so a milestone arriving
in month 24 already counts for the actions available at turn 2); then the user picks an action, the `effects` of its
outcome (drawn at the luck of the decision) become `PendingChange`s (section 5.3), and a shock may add its own (`docs/decision-tree.md`).

**Every month `t → t+1`** (full rules and sources: [`docs/simulator.md`](simulator.md)):
0. (At the **start** of the month.) The `PendingChange`s with `month <= t` are applied (life, income, event expenses, a
   new loan) and life changes emit `LIFE_CHANGE`; so a new job already counts for that month's bonus.
1. **Trends, every month** (from the second one, 1/12 of the yearly rate): `monthlyIncomeChf` grows with the wage
   index × the career step for the age and occupation (career only while working); `monthlyRentChf` with the rent
   index; learned flows with inflation (`macro.json`). Event expenses keep the amount the event set.
2. **Flows of the month** from `flow-model.json` and every categorical and numeric field of the state (the model uses
   the ones the data support: city, studying, employment): salary and rent, plus groceries, insurance, travel,
   December bonus, tuition, unexpected expenses... Event expenses are added as they are; an event's TUITION replaces
   the learned tuition.
3. Loan: `due = principal × (1 + annualRate/12)`; `pay = min(monthlyPayment, due)`; `principal = due − pay`.
4. **Financing**: if `cash_t < 0`, interest is paid: `financing_t = |cash_t| × financingRateAnnual / 12`.
5. `cash_{t+1} = cash_t + net` (the model never writes cash directly).
6. Investments: `investmentsChf × (1 + investmentReturnAnnual/12)`.
7. Moments: `CASH_NEGATIVE` when crossing below zero, `CASH_RECOVERED` when back above, `GOAL_REACHED` when the goal's
   basis (cash or net worth, see `docs/financial-statement.md`) reaches the target before its date, `GOAL_MISSED` if the
   date arrives first. `LOW_POINT` (lowest cash) is marked at the end of the game.
8. The month's `cashFlow` is recorded in the new `FinancialStatement`.

**Attribution:** every month each cash-flow category is added to its `AttributionItem` (`income:<key>`,
`expense:<key>`, `loan_interest`, `financing_cost`, `investment_growth`).

Invariants the tests must check:
- Accounting consistency: `netWorth_{t+1} − netWorth_t = income − expenses − interest − financing + asset growth` (tolerance 0.01 CHF).
- Statement identities (`docs/financial-statement.md`, section 5).
- Attribution: `startNetWorth + Σ items = endNetWorth`.
- Each action's probabilities sum to 1 (3 cases, or one certain NEUTRAL case for NOTHING); NOTHING is always in the pool.
- Same seed ⇒ same result; in SAME_LEVEL every decision at the same depth gets the same `luck`.
- A loan is paid down to 0 within its term.

## 8. Data and the simulator

The challenge's **synthetic** data in `ai-financial-twin-lauzhack-2026/Data` (1,200 profiles, linked by `profile_id`)
plus public Swiss data (`data/download.sh`). How each column ends up in the `FinancialStatement`:
`docs/financial-statement.md`, section 3. How time moves: [`docs/simulator.md`](simulator.md); how it is learned from the data, step by step: [`docs/how-the-simulator-learns.md`](how-the-simulator-learns.md).

| File | Content | Goes to |
|---|---|---|
| `synthetic-profiles.csv` | Age, city, canton, country, employment, household, cash, income, rent | Opening statement of a dataset profile (Alexia) |
| `synthetic-accounts.csv` | Cash account and opening balance | `accounts` |
| `synthetic-assets.csv` | Cash (duplicate, counted once) and investment portfolio | `investments` |
| `synthetic-liabilities.csv` | Personal loans (snapshot only, payment 0, **not amortised**) | `liabilities` (assumed payment: 60-month annuity) |
| `synthetic-goals.csv` | Goals with amount, date and priority | `goals` |
| `synthetic-transactions.zip` | 552,295 transactions by category (24 months) | **Flow model** (`tools/flow_model.py`) |
| `synthetic-cash-balances.csv` | Monthly cash series (24 months per profile) | Validation of the simulator |
| `scenario-assumptions.csv` | Tuition and study length for profiles P00001-P00120 (scenario S001 only) | Not used: events carry their own numbers |
| `scenario-catalog.csv`, `life-events.csv` | 120 scenarios; 600 proposed (not executed) events | Inspiration for events |
| `data/raw/*` (BFS, SNB, World Bank, Eurostat, BIS) | Inflation, wage index, rent index, wages by age, unemployment... | **Macro trends** (`tools/macro.py`) |

What the flow model learned from the whole dataset (one rule for everybody, no segments):
- It tests every field of the statement that describes the person (15: categorical and numeric). Living costs depend on
  the **city** (Fribourg 0.94 … Zurich 1.29) and on **studying** (−20 %); age, household, income, rent, cash, debt,
  investments, occupation, housing and family change nothing.
- December bonus: 57 % of the time, only when employed or self-employed, ≈ 0.59 × income. Tuition in February and
  September when studying. Travel in February and August. Unexpected expenses in 7 % of the months.
- Out-of-sample (240 unseen profiles, 24 months from the opening state only): median error of closing cash CHF 1,214.
- The ledger has no trend (2026 = 2025): over 10 years growth comes from the macro trends.
- The data are synthetic: the model rebuilds the generator, not real behaviour. We must say so.
- Default financing rate: 8.5 % (maximum in `synthetic-liabilities.csv`; loans range from 2.5 % to 8.5 %).

## 9. Analysis: the tree of decisions and sensitivity

**The tree of decisions** ([`decision-tree.md`](decision-tree.md)). The user explores it: every node is a decision
taken, and going back to a moment opens another branch. With the luck mode SAME_LEVEL, two branches from the same node
get the same luck, so the difference between them is what the decisions did. The automatic parallel lives (other first
choice, optimal strategy by expectimax) were removed with the action pool: comparisons are between lives the user
decided. An exact optimal strategy over the pool is possible later (5 levels × the available actions × 3 cases).

**Sensitivity and break-even point** ("your story would change if..."). For the first decision, each parameter in
`Assumptions.sensitivity` is moved to its low and high value (salary, tuition and living-cost multipliers; months of
job search; inflation; interest). The utility gap between two actions is computed and, by bisection, the value where the
better one flips. Example: *"The master's stops paying off if your salary afterwards drops below CHF 5,600"*.
It answers the judges' first question.

**Constraints.** User's minimum cushion (`minCashChf`) and negative cash financed with interest. With negative cash the
pool offers a personal loan (`maxCashChf: 0`): a constraint breach becomes a possible decision.

**End-of-game statistics (MVP):** final net worth, lowest cash and when, months negative and below the cushion,
financing cost, goals reached; the map compares the explored lives.

## 10. LLM: where the answers come from and how not to pay

### Where the content comes from
The LLM knows nothing about the user. It only knows what is passed in `ChatContext`:

| Prompt part | Content | Produced by |
|---|---|---|
| System prompt | Role (future self or parallel self), tone, rules | Dev C (by hand) |
| Story | `StoryBeat`s of the life (decisions, shocks, life changes), facts and milestones with their labels | The engine + `facts.json` |
| Numbers | `Stats`, `Attribution`, `SensitivityItem`, `FinancialStatement`s | The engine |
| Assumptions and limits | `Assumptions.sourceNotes`, `macro.json` sources, what is learned from data and what is assumed | JSON |
| Question | Free text | The user |

Rules: *use only the numbers and facts in the context; if they are not there, say you do not know; cite the age or
moment; remind the user it is a simulation and not financial advice.*
- **During the game**: each case's narrative is fixed (`CaseOutcome.narrative`), no LLM.
- **At the end**: full chronicle (`chronicle`) and chat. **Plan B**: chronicle from text templates per kind of moment.
- The chat explains the story and the results; it does **not** propose new scenarios (out of the MVP).

### Keeping it free
Free-tier limits and terms change: **check them before relying on them**.

| Option | Cost | Where | Note |
|---|---|---|---|
| Local Ollama (Llama, Qwen, Gemma…) | €0 | Desktop | Needs RAM/GPU; a small model answers worse in Spanish. Android can call it over the local network |
| APIs with a free tier (Gemini, Groq, OpenRouter "free"…) | €0 within the limit | Android and Desktop | Request limits; needs a key and network |
| Hackathon credits | €0 | Both | Ask the organisers |
| Templates (plan B) | €0 | Both | Not a real conversation |

Recommendation: **Ollama during development**, a free API in the demo if the wifi is reliable (Ollama as backup) and
**templates always ready**. Privacy: with Ollama, what the user types never leaves their machine. Never put keys in the repo or the app.
